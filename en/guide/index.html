Guide

How to record, target and schedule tasks — plus the parts that surprise people.

This guide covers the things that are not obvious from the buttons: how targeting really works, why a fixed delay fails where a wait succeeds, what each auto-start mode costs you, and what to check when a task stops working.

Before you start

Two permissions are required, and each does something specific:

  • Accessibility service — this is what performs clicks and gestures, and what lets clicktap read the controls it needs to find. Without it, replay cannot work at all.
  • Display over other apps — needed to show the floating recorder bar and the capture layer during recording.

Three more are optional and only matter if you use the matching feature:

  • Notification access — for the Message trigger, which reads notification text.
  • Alarms & reminders — makes scheduled runs fire on time. Without it Android may delay them. On Android 14 and above, full-screen notification access is also required for a locked-screen reminder to wake the display; without it the reminder still rings and vibrates.
  • Ignore battery optimisation — reduces the chance that a run is interrupted in the background.

Permissions are toggled in system settings, not inside the app: tapping a switch opens the relevant settings page, and the status updates when you come back.

Recording a task

  1. Tap Start recording. A floating bar appears.
  2. Just use the app you want to automate the way you normally would. Your taps are recordedand performed, so the underlying app still responds — you are not driving a dead screen.
  3. Pause or finish from the floating bar whenever you like.
  4. Give the task a name. The name is only a label; it does not affect replay.

Multi-finger gestures

Draw with two or more fingers; lifting all fingers records one gesture. Up to three fingers are supported. Gesture paths come from the recording and cannot be edited finger by finger — to change one, record it again. If a gesture needs the screen to be clear, you can record it on a blank screen.

How a step finds its target

Every step has a targeting method. This is the single biggest factor in whether a task keeps working, so it is worth getting right.

By control

The most reliable option. A step can match a control by resource ID, by visible text, or by content description, and you can combine several conditions with AND or OR. The best way to fill it in is to point at the control on the real screen and let clicktap read it, rather than typing it by hand.

A caution about text-only matching: text and description are matched by substring, so a small wording change still hits — but pairing a text match with a resource ID is more reliable when the app uses stable IDs.

By coordinates

Coordinates are recorded as screen ratios rather than pixels, so a task recorded on one phone normally still works on another with a different resolution. Treat this as the fallback: it cannot tell whether the screen is in the state you expected.

By text recognition (OCR)

Use this when a control has no usable ID — canvas UIs, web views, games.

  • You frame up to three search regions on the screen, and the recognised text in them is offered for one-tap selection.
  • The click lands on the centre of the matched text. If several matches fall inside one region, the one nearest where you tapped wins.
  • Regions are OR-ed and tried in order; the first hit stops the search.
  • Matching ignores case, and a partial hit counts.
  • The polling interval defaults to 500 ms and is clamped to 350–2000 ms. The floor is Android's screenshot throttle — about three per second — not recognition speed, so smaller values are simply refused by the system. Wait-until-found requires Android 11 or above, because it needs the screenshot API.

Waiting for the page, instead of a fixed delay

A step can wait until its target actually appears before tapping. This is the difference between a task that survives a splash ad and one that does not: a fixed sleep usually expires after the ad has already gone, and then the tap lands on nothing.

The wait timeout is the maximum time to keep looking. Around 8000 ms is a good starting point for splash screens. Setting it to 0 means "do not wait" — the step runs immediately.

The same idea applies to text recognition: a wait of 0 recognises once, while a larger value re-recognises at the polling interval until the text appears. Use it when a page needs a moment to render.

Loops and the flow chart

Steps can be grouped into a loop that repeats up to five times, and loops can be nested. A loop is a contiguous range of steps, so loops cannot cross each other. When a step inside a loop cannot find its target you choose the consequence: stop the whole run, or abandon the rest of that iteration and continue with the next one.

The flow chart view shows the same task as a diagram, which is far easier to check than a long list once loops are involved.

Auto start

A task can run itself in one of three ways. Only one mode can be active on a task at a time, and manual replay always works regardless.

  • Scheduled — pick weekdays and a time. You also choose where replay begins: return to the home screen first (recommended), launch the target app first, or replay right where you are.
  • Message — choose an app and keywords. Any keyword found in a notification's title or body triggers the run. You can ask clicktap to open the notification first, so replay starts on the right page; if the notification cannot be opened it falls back to the start point. One caveat: if the source app hides message previews, only placeholder text such as "1 new message" is readable, and your keywords will not match.
  • App launch — choose one or more apps and which window events to watch. The "window or page changed" event is the usual signal for "the app opened". You can also watch for content changes, but be aware of the cost: that event fires constantly while lists scroll, text updates or animations run, which wakes the accessibility service repeatedly and can cause stutter and extra battery drain. A replay interval controls how often the task may run again inside the same app session; events during the cooldown are logged as skipped.

A scheduled task that fires while the screen is off or locked can wake the device and alert you, by vibration or by a sound — including a custom sound file of your choosing.

The execution log

One log answers both of the questions you actually have: why a run did not start, and which step failed when one did. Entries are grouped into runs, and long silence separates one run's segment from the next. You can record every step for detail, or filter straight to failures.

Debug mode adds a replay bar during automatic runs and overlays the gesture traces while recording and replaying, which is the quickest way to see where a tap actually landed. Manual replay always shows the bar.

Backups, imports and the Playbook

  • Backups. Export one task or a whole selection as a .clicktap file and import it on another device. The format is a zip containing a manifest and one JSON file per task, plus any custom reminder sound you attached.
  • gkd rules. Subscription rules in gkd's JSON5 format can be imported by URL or from a file, and run as always-on matching. Enable or disable each subscription and rule group from the list.
  • Sharing. A published package is stored and published exactly as it is, with nothing removed — including step notes, matched on-screen text, notification keywords, target package names and any embedded reminder sound. Readthe privacy policy, section 6 before you publish anything, and use the review list the publish page shows you.
  • Importing someone else's package. clicktap disables incoming triggers on import, so an imported task never starts running by itself. Read its steps before you run it.

When a task stops working

Almost always one of these, in this order:

  1. The app changed its interface. Check the execution log for the failing step, then re-target it. Control IDs survive reskins better than text.
  2. The screen was not where you expected. Add or increase a wait timeout on the step before the one that failed, or set a start mode that returns to the home screen first.
  3. A permission or battery setting changed. Accessibility services are sometimes disabled by the system after an update; check the runtime status on the home screen.
  4. A popup appeared that your recording never saw. Record the dismissal once and target it by ID or text, with a generous wait.

clicktap requires no root, and works from Android 10 onwards. Text recognition needs Android 11 or above. Behaviour is kept consistent across supported versions.

Selecting a control on the real user interface is more reliable than typing it. You can still type the ID, text or description by hand.
